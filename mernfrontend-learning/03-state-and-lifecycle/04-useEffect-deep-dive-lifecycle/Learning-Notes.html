3. The React Render-Commit-Paint-Effect Pipeline

Understanding the exact sequence of events in a render cycle prevents subtle timing bugs.

The Pipeline — Step by Step

1. State Change→ 2. Render Phase→ 3. Commit Phase→ 4. Browser Paint→ 5. Cleanup (Prev)→ 6. Setup (Current)
  1. State Change / Trigger — e.g. setCount, API response
  2. Render Phase — Component Function Executes, React generates Virtual DOM snapshot
  3. Commit Phase — React updates Real DOM nodes
  4. Browser Paint — User sees new UI on screen
  5. Cleanup Function of PREVIOUS effect runs
  6. Setup Function of CURRENT effect runs

Key Takeaways

  • useEffect is non-blocking (asynchronous): It runs after the browser paints. So network calls and heavy effects don't freeze typing / clicks / animations.
  • User sees UI first: If effect immediately triggers another state update, user may momentarily see first state before second render paints.

⚠️ The Subtle Timing Bug

The bug is NOT that useEffect is late — it's that the user sees the WRONG UI for one frame before the effect fixes it.

Render → Commit → PAINT (user sees WRONG UI) → Effect → Render → PAINT (correct)

Classic Example — Flicker Bug

function Tooltip() {
  const [pos, setPos] = useState({ top: 0, left: 0 });
  const ref = useRef();

  useEffect(() => {
    const rect = ref.current.getBoundingClientRect();
    if (rect.right > window.innerWidth) {
      setPos({ top: 0, left: -100 }); // move it left
    }
  }, []);

  return <div ref={ref} style={pos}>Tooltip</div>;
}

What user sees:
1. Paint 1: Tooltip at 0,0 — wrong place
2. Effect runs → setPos
3. Paint 2: Tooltip jumps to correct place

That jump = flicker / layout shift.

✅ The Fix — useLayoutEffect

Use it for anything that reads layout and synchronously re-renders before paint.

useLayoutEffect runs: Render → Commit → Cleanup → Setup → PAINT
No paint in between, user never sees intermediate state.
HookUse For
useEffectDo this AFTER user sees it — fetch, subscribe, log, analytics
useLayoutEffectFix this BEFORE user sees it — measure DOM, set scroll, position, prevent flicker
// BUGGY - runs AFTER paint
useEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  if (rect.right > window.innerWidth) setPos({ left: -100 });
}, []);

// FIXED - runs BEFORE paint
useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  if (rect.right > window.innerWidth) setPos({ left: -100 });
}, []);

Second Bug — Cleanup Order + Race Condition

Cleanup runs on every dependency change, BEFORE new setup — not only on unmount.

useEffect(() => {
  let cancelled = false;
  fetch(`/api/user/${userId}`).then(data => {
    if (!cancelled) setUser(data);
  });
  return () => { cancelled = true; };
}, [userId]);

Without cancelled flag, slow request for userId=1 can finish after userId=2 painted and overwrite UI with stale data.

🔍 How Pros Find It In Real Code

Search for this pattern:

useEffect + getBoundingClientRect
useEffect + scrollHeight / offsetWidth / offsetTop
useEffect + setState (right after measuring DOM)

Ask 1 question: "Am I measuring DOM and then fixing UI?"
YES → useLayoutEffect  |  NO → keep useEffect

Real Examples

  • Dropdown opens right, then jumps left
  • Chart renders wrong height, then resizes
  • Chat scrolls to bottom, but user sees jump from top first
  • Modal opens center, then shifts

One-line summary: If your effect CORRECTS what was just painted, useEffect is too late.

🎤 Interview Question

Q: When would you use useLayoutEffect over useEffect?
A: When I need to read DOM layout and synchronously update state to fix layout before browser paints, to avoid flicker. For fetching, subscriptions, timers — useEffect.
